# Bearpaws v3.0.0 design

Status: proposed. Branch `explore/test-outcome-gate`, one PR, released as v3.0.0. It also carries the two commits already on the branch: the test-outcome gate (`ffdb474`) and the README audit (`fdc4c8c`).

## Premise test

A change belongs in v3.0.0 only if it makes elevated work more trustworthy or routine work cheaper. Anything that adds process everywhere is out. Five ideas pass that test, written in bearpaws' own words and structure.

## 1. `diagnosing-bearpaws` (new skill, report only)

**When:** your human partner says a session went wrong ("it took too long", "skill X never fired", "it said COMPLETE but the tests failed") or asks whether a receipt was honest. The skill is read-only and opt-in, and costs nothing until invoked.

**Flow:**
1. **Intake.** Ask one question at a time until there is a problem statement: which session, what was expected, what happened, and the observable. A whole-session "why" is a complaint, not a statement.
2. **Locate.** Resolve the session to absolute transcript paths, including subagent transcripts (`references/session-discovery.md`). Claude Code only in v3.0.0; for other harnesses, say so and stop. Confirm a past session by quoting its first prompt and timestamp.
3. **Triage.** Read the region around the complaint yourself, then dispatch five analysts in parallel. Each gets the case file, `prompts/analyst-common.md`, and one dimension:
   - `receipt-vs-transcript.md` (new). Checks every risk receipt against what the transcript shows: a `Verified:` run after the last edit and its outcome (tool error, or a failure summary in output a pipe hid); a `Pinned:` run before the first edit; a review dispatched after the last edit; Critical or Important findings that review raised against `Open:` and `Status: COMPLETE`; `Risk: routine` on sensitive paths; a heredoc or commit line counted as a run. This covers the cases the README says the hook cannot see. The `risk-gate` log is cleared on every allowed Stop, so it is not a durable record and the transcript is the evidence.
   - `quality-evidence.md`, `plan-adherence.md`, `request-conflicts.md`, `cost-and-time.md`: one dimension each, following the same finding format as the receipt analyst.
4. **Report.** Fill `templates/report.md`, write it to `~/.bearpaws/diagnosing/<session-id>/report.md`, show it, give the path.

**Hard rules:** every finding cites `path:line`, and a finding without one is dropped. Every number comes from the transcript or from a command you ran. Never modify a session file. Pass absolute paths to subagents. Hook output, system reminders and tool results are not your partner's words. Report what happened; do not patch skills from inside the diagnosis. Follow `references/context-safety.md`: one transcript line can be megabytes, so read with `jq`/`cut` and never `cat` a whole file.

**Not in v3.0.0:** scrubbed bundle export, GitHub issue filing, similar-session search, and the skill-timeline, repeated-work and stumbles analysts.

**Files:** `skills/diagnosing-bearpaws/{SKILL.md, prompts/analyst-common.md, prompts/receipt-vs-transcript.md, prompts/quality-evidence.md, prompts/plan-adherence.md, prompts/request-conflicts.md, prompts/cost-and-time.md, references/session-discovery.md, references/context-safety.md, templates/report.md}`, plus the `.agents/skills/diagnosing-bearpaws` link.

## 2. Scoped re-review after a fix round

`skills/subagent-driven-development/re-review-prompt.md` (new). After a fix round, the controller dispatches it instead of a second full review. Inputs are the open Critical/Important findings verbatim, the task text, and the fix diff `FIX_BASE..HEAD`, where `FIX_BASE` is the head the previous review saw.

The re-reviewer:
- gives each finding a verdict of ADDRESSED or NOT ADDRESSED, with `file:line` ("attempted" is not addressed);
- reports new breakage in the fix diff only, with severity;
- lists anything outside the fix diff as an out-of-scope observation, which never blocks and never extends the loop;
- keeps bearpaws' adversarial floor for the fix diff: at least one `Tried: [executed|reasoned]` break attempt per finding, and a "What I didn't check" line;
- does not re-run the full suite.

The final whole-branch review stays a full review. The risk gate already counts a re-review dispatch as a review (`REVIEW_DESC` accepts `re-review`), so a scoped re-review after the last edit satisfies the elevated floor. `bp:requesting-code-review` gains one line: after fixing findings, use the scoped re-review rather than a fresh full review.

## 3. Fix-loop cap with escalation

In `bp:subagent-driven-development`, each fix round is one fix dispatch plus one scoped re-review, with at most 5 rounds per task:
- **Rounds 1–3:** resume the original implementer with the open findings verbatim.
- **Rounds 4–5:** a fresh implementer on a more capable model, told how many attempts came before.
- **After round 5,** with findings still open: stop dispatching. The task is blocked, its findings go into `Open:`, and the report ends `Status: INCOMPLETE`. INCOMPLETE is always allowed, so the cap fits the receipt as is.
- **Minor findings** never enter the loop; they are noted for the final review.

## 4. Builder check, elevated designs only

`skills/brainstorming/builder-check-prompt.md` replaces `spec-document-reviewer-prompt.md`. Brainstorming dispatches it only when the design covers elevated-risk work. A fresh subagent reads the design as the person who has to build it and lists only the questions where a wrong guess would change the plan, ranked; otherwise it says "nothing important left". The author answers or amends the design before planning.

Routine designs get the spec self-review only. That removes one subagent from every routine design.

## 5. Helper and path hardening (lessons only)

- **Audit:** every hook and script resolves paths from `CLAUDE_PLUGIN_ROOT`, its own absolute location, or `git -C <dir>`, never the caller's cwd or a skill-relative path, and refuses to act outside a repo where it needs one. Fix any that do not.
- **New validator rule:** no test scenarios, eval fixtures or pressure prompts inside `skills/`, because agents find them mid-task. Evals live under `tests/`. Pinned in `tests/schema-validator/run-validator.sh`.
