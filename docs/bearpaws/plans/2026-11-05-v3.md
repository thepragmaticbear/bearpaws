# Bearpaws v3.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use bp:subagent-driven-development (recommended) or bp:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Status:** Approved design: [2026-11-05-v3-design.md](2026-11-05-v3-design.md)

**Goal:** Ship bearpaws v3.0.0 on branch `explore/test-outcome-gate` as one PR. It adds `diagnosing-bearpaws`, a scoped re-review, a fix-loop cap, a builder check for elevated designs, and path and fixture hardening.

**Architecture:** Skills are markdown with a compact XML-like structure (see `docs/skill-structure.md`; tags are whitelisted by `tests/schema-validator/run-validator.sh`). Every skill change follows bp:writing-skills: run a baseline scenario in a fresh subagent or `claude -p` run (RED), capture the failure, write the minimum text that fixes it, then re-run (GREEN). Evals live under `tests/<name>-eval/` and follow the pattern of `tests/drift-eval/` (`setup.sh` builds a fixture, `run.sh` runs `claude -p` N times, `score.py` scores the result, `test_score.py` pins the scorer, `evidence.md` records RED and GREEN).

**Tech Stack:** Markdown skills; bash 3.2-compatible scripts; Python 3 stdlib scorers; the `claude` CLI for evals (Sonnet, `BENCH_MODEL` overrides it).

**Conventions every task follows:**
- Do not name any other skills toolkit or plugin (including the one bearpaws was forked from) anywhere in skills, tests, evals, release notes, commits or the PR. The README's existing attribution and comparison sections are the only place the fork's origin is named, and they stay as they are.
- Do not edit the Red Flags tables or the tuned wording of existing skills unless the task says to.
- Receipts and commit trailers follow CLAUDE.md. A commit carries `Risk:`, `Verified:`, `Not checked:` and `Status:`, with no Co-Authored-By.
- After each task, run `tests/schema-validator/run-validator.sh` and the suite named in the task.

- [ ] **Step 1: Build the fixture.** In `setup.sh`, add a `rereview` branch with a small Python module and two commits.
  - Commit A (the reviewed head) has two planted defects:
    - (F1) `refund()` accepts a negative amount;
    - (F2) `refund()` does not check the cumulative cap.
  - Also add a pre-existing unrelated issue that commit A does not touch: a `report()` function that builds SQL by string concatenation.
  - Commit B (the fix) fixes F1, leaves F2 unfixed, and adds a new bug: the negative check uses `< 0`, so zero is accepted, while the task says amounts must be positive.
  - `report-rereview.txt` lists F1 and F2 verbatim as the open findings. `task-rereview.txt` states the requirement: amounts must be positive and cumulative refunds may not exceed the total.
- [ ] **Step 2: RED.** Run the current full-review template as the re-review, the way the SDD loop does today: `FIXTURE=rereview AGENT_PROMPT=agents/code-reviewer.md tests/review-eval/run.sh skills/requesting-code-review/code-reviewer.md rereview-red 3`. Score: F2 verdict not addressed, the zero-amount bug caught, the SQL issue blocking or not, and cost. Record the result in `rereview-evidence.md`. Expected weakness: there is no per-finding verdict, the SQL issue is raised as blocking (or Important) and extends the loop, and the cost is full-review cost.
- [ ] **Step 3: Write `re-review-prompt.md`.** Adapt from the design §2. It must contain the following.
  - **Placeholders:** `[TASK_TEXT]`, `[FINDINGS]` (verbatim, one per bullet), `[FIX_BASE_SHA]`, `[HEAD_SHA]`.
  - **Scope:** the findings list and `git diff [FIX_BASE_SHA]..[HEAD_SHA]` only.
  - **Read-only checkout:** the re-reviewer does not mutate the working tree, the index, HEAD or branch state.
  - **No subagents:** "You do not dispatch subagents".
  - **Tests:** do not re-run the suite; run one focused test only when reading leaves a specific doubt.
  - **Output sections, in order:**
    1. `### Finding Verdicts`: each finding ADDRESSED or NOT ADDRESSED with `file:line`; "attempted is not addressed".
    2. `### New Breakage in the Fix Diff`: with severity Critical, Important or Minor, using the same severity rules as `skills/requesting-code-review/code-reviewer.md`, copied as a one-sentence pointer rather than duplicated.
    3. `### Break Attempts`: at least one `Tried: [executed|reasoned] X — Y` line per finding, against the fix diff.
    4. `### What I didn't check`.
    5. `### Out-of-Scope Observations`: never blocking, never extends the loop.
    6. `### Verdict`: "All findings addressed, no new Critical/Important" or "Findings remain open: …".
  - **Dispatch:** the description must start `Re-review` so the risk gate counts it. Model: the cheapest that handles review (the fix diff is small).
- [ ] **Step 4: Wire it in.** In SDD's routine and elevated steps, replace "implementer fixes → re-review → repeat until ✅" with "implementer fixes → scoped re-review (./re-review-prompt.md) of the open findings and the fix diff → repeat (see Fix loop)". Do the same in the rules list. Add `<see file="re-review-prompt.md"/>`. In requesting-code-review's "Act on feedback" step, append: "After fixing, verify with the scoped re-review (bp:subagent-driven-development's re-review-prompt.md) rather than a second full review; the final whole-branch review stays full."
- [ ] **Step 5: GREEN.** Run `FIXTURE=rereview tests/review-eval/run.sh skills/subagent-driven-development/re-review-prompt.md rereview-green 3`. `render.py` must fill `[TASK_TEXT]`, `[FINDINGS]`, `[FIX_BASE_SHA]` and `[HEAD_SHA]`, so extend it and `test_render.py`.

  Pass, in 3 of 3 runs:
  - F1 is ADDRESSED and F2 is NOT ADDRESSED;
  - the zero-amount bug appears under New Breakage at Important or higher;
  - the SQL issue appears only under Out-of-Scope;
  - mean cost is below the RED mean.

  Record the result in `rereview-evidence.md`.
- [ ] **Step 6:** Run `python3 tests/review-eval/test_score.py`, `python3 tests/review-eval/test_render.py`, the validator, and `tests/review-eval/routing.sh` if it is affected. Commit (`Risk: routine`).

**Files:**

- [ ] **Step 2: Write `score.py`.** Pass when the final reply ends `Status: INCOMPLETE`, its `Open:` line names the finding, and it does not dispatch or describe a round 6. Pin the scorer with `test_score.py`, using one passing and two failing replies.
- [ ] **Step 3: RED.** Run `tests/fixloop-eval/run.sh skills/subagent-driven-development/SKILL.md red 3` against the current SKILL.md. Record the result in `evidence.md`. Expected: the agent proposes another round, or ends COMPLETE.
- [ ] **Step 4: Write the section.** Add `## Fix loop` to SDD:
  - A fix round is one fix dispatch plus one scoped re-review.
  - At most 5 rounds per task.
  - Rounds 1–3: resume the original implementer with the open findings verbatim.
  - Rounds 4–5: a fresh implementer on a more capable model, told how many attempts came before.
  - After round 5, with findings open: stop dispatching. The task is blocked, its findings go in `Open:`, and the report ends `Status: INCOMPLETE`.
  - Minor findings never enter the loop; they are noted for the final review.
  - Each implementer re-runs the tests covering the amended code and reports the command and output before the re-review is dispatched.

  Keep the section under 15 lines.
- [ ] **Step 5: GREEN.** Run `tests/fixloop-eval/run.sh skills/subagent-driven-development/SKILL.md green 3`. Pass: 3 of 3. Record the result in `evidence.md`.

Write it from what you observe on disk with `ls` and `jq -c 'keys'`. `context-safety.md` covers `wc -l` first, `jq -c 'select(...)' | cut -c1-400`, never a whole-line `cat`, and line numbers via `grep -n`.
