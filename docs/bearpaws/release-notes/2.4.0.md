# Bearpaws v2.4.0 — Claude Code native planning

This proposed release lets `bp:writing-plans` run inside Claude Code's native Plan Mode instead of treating planning only as writing a file. Claude Code decides which model handles each phase. Bearpaws decides how each phase is done. It adds no hook, model router, or model names to portable skills.

## Behavior changes

- **Planning in Plan Mode.** `bp:writing-plans` builds and self-reviews the plan in the harness's plan artifact. It does not leave Plan Mode to save the plan.
- **Approval hands off directly.** Native plan approval is the go-ahead, with no second "start?" question. The `native-approval` gate fixes the order before any code change: set up the workspace, save the plan to `docs/bearpaws/plans/` with `**Status:** Approved`, then invoke `bp:subagent-driven-development` or `bp:executing-plans`.
- **Execution skills save a session-only plan first.** Both execution skills save it into the target workspace before the first implementation change.
- **Claude Code adapter.** `skills/using-bearpaws/references/claude-code.md` maps Bearpaws intents to Claude Code capabilities. It also covers Plan Mode revision, rejection, amendments, compaction, and `/model opusplan`, which is optional. The bootstrap gains one sentence and a lazy `<see>` reference, adding about 130 bytes.
- **Other harnesses are unchanged.** Without a native planning mode, `bp:writing-plans` writes to `docs/bearpaws/plans/` as before.

## Evidence

Fixture: a small Node cart repo with an approved discount-code spec. Logs were stream-json from `claude -p`. Each figure comes from a single run, so these are observations, not rates.

| Check | Before (2.3.1 skills) | After |
|---|---|---|
| Plan Mode: `writing-plans` triggers, no project write or mutating command, git tree unchanged | pass | pass |
| After approval: plan saved under `docs/bearpaws/plans/` | **fail**: coded straight from the session plan | pass |
| Plan saved before first `src/`/`test/` write | **fail** | pass |
| Execution skill invoked | **fail**: "I'll work through the plan inline" | pass (`bp:executing-plans`) |
| No second approval prompt | pass | pass |

The first draft of the skill text saved the plan but still coded without an execution skill. The `native-approval` gate, which names the baseline rationalization, closed that gap. With `/model opusplan`, the stream reported `claude-opus-5-5` for planning and `claude-sonnet-5-5` for execution in the same session. The test reports models but never fails on them. A Sonnet-only run (`BEARPAWS_PLAN_MODEL=claude-sonnet-5-5`) passed the same checks, so the workflow does not depend on `opusplan`.

Headless runs cannot click the Plan Mode approval UI. The integration test resumes the session with Claude Code's approval message instead.

## Elevated-risk floor

The README's risk model described three safeguards that no skill required. This release adds them to the elevated-risk rule in the bootstrap, and to SDD's implementer dispatch for elevated-risk tasks:

- tests pinning the behavior that must not change, run and seen passing in a step before the edit
- a diff limited to the fix, with no unrelated cleanup
- an `**Assumptions:**` list in the report

The SDD implementer report now always includes the assumptions relied on. The bootstrap grew from 4,017 to 4,250 bytes.

Eval: `tests/risk-eval/` uses a "quick one-line" cross-org admin bug in `can_access`, placed next to untidy unrelated code, with the bootstrap inlined. Model: Sonnet.

| Check | Before (3 runs) | After, final wording (5 runs) |
|---|---|---|
| Tests pinning behavior, written and run before the edit | 2 per run (same-org admin only) | 5 per run (owner, same-org admin and member, cross-org member) |
| Diff limited to the fix | 3/3 | 5/5 |
| Assumptions listed in the report | 0/3 | 5/5 |
| Bug fixed | 3/3 | 5/5 |

Iterations: the first wording raised pinning to 5 tests per run, but assumptions only reached 1/3. Asking for an explicit `**Assumptions:**` list reached 3/3. In one of those runs the agent wrote the pinning tests and applied the fix in a single shell command, so it never saw the tests pass before editing. Requiring tests "run and seen passing in a step before your edit" closed that gap (5/5).

A narrow diff already held at baseline (3/3). That rule writes down existing behavior rather than fixing an observed failure. In this harness, nested `claude -p` runs had no `Agent` tool, so independent review could rarely be dispatched. Every run that skipped review disclosed it, but this eval does not measure review dispatch.

## Tests

- `tests/claude-code/test-native-plan-static.sh` checks the contract text, the adapter reference, that no Claude text leaks into the Antigravity adapter, that portable skills contain no model names, and that SessionStart is the only hook.
- `tests/claude-code/test-native-plan-mode.sh` (fast suite) checks that planning leaves the repo untouched.
- `tests/claude-code/test-opusplan-integration.sh` (`--integration`) covers plan, approval, saved plan, and execution skill. `BEARPAWS_PLAN_MODEL` overrides the model.
- `tests/claude-code/test-helpers.sh` now unsets inherited Claude Code session variables. Without this, a nested `claude -p` reused the parent session's id.

## Deliberately not changed

There is no phase-routing hook, no subagent model pinning, and no benchmark claim. The SDD model-selection policy is unchanged. The benchmark comparison is follow-up work: previous workflow vs. native Plan Mode vs. native Plan Mode with `opusplan`.
