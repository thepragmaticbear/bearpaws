# Bearpaws v3.0.0: test-outcome gate, session diagnosis, scoped re-review, fix-loop cap, builder check

## Why 3.0.0

- **The gate is stricter.** A reply the risk gate allowed in v2.9.0 can be blocked now: a failed test run, or one launched in the background, no longer satisfies `Verified:` or `Pinned:`.
- **`hooks/hooks.json` gains `PostToolUseFailure`** (Bash only), so the plugin registers one more hook event.
- **The brainstorming flow changes.** `spec-document-reviewer-prompt.md` is gone. An elevated-risk design now gets a builder check; a routine design gets the self-review only.

## Test-outcome gate

`risk-gate` now looks at how each test run ended, not only whether one ran.

- A test command that exits nonzero is logged as failed (`PostToolUseFailure`).
- A pipe, `;`, `|| true` or an earlier `&` can hide a run's exit status. Such a run is logged as failed when its output, with ANSI codes stripped, has a failure summary line from a known runner: pytest, unittest, jest/vitest, go, cargo, rspec/bats, mocha, TAP, phpunit, `node --test`, ctest, or `N TEST(S) FAILED`.
- A background launch (`run_in_background`, or a trailing `&`) is not a run.
- `Verified:` is blocked when the last test run after the last edit failed.
- `Pinned:` rests on the last run before any edit, which must have passed. The failing-first run after a test edit does not count against it.
- A pass followed by a failure is not carried into the next turn.

The README's list of known limits now names what the gate still misses: a failing run with a hidden status and no recognized summary line, a script that hides its own status (`"test": "jest || true"`), and a chained command that fails after passing tests.

## `bp:diagnosing-bearpaws`

A new Process skill. It reads a past Claude Code session's transcript and reports why the session went wrong and whether its risk receipt matched what it did. It is report-only and changes nothing.

- Every finding cites a full absolute `path:line`, and the diagnoser re-prints each cited line before reporting.
- Five dimension prompts (cost and time, plan adherence, quality evidence, receipt against transcript, request conflicts) can go to analyst subagents.
- The analysts are optional when the main and subagent transcripts together are under 100 KB and the diagnoser reads every line; Coverage gives the byte count. At or above 100 KB all five are dispatched.

**Evidence (`tests/diagnose-eval`, Sonnet, n=3).** The fixture is a 35-line session that hides a failing pytest run behind a pipe, leaves a reviewer's Important finding out of `Open:`, and ends `Status: COMPLETE`.

| Arm | Pass | Mean cost |
|---|---:|---:|
| No skill | 0/3 | $0.116 |
| Final skill text (round 7) | 3/3 | $0.192 |

Without the skill, every run described both problems, but cited wrong line numbers or none. Runs that dispatched all five analysts cost $0.42–0.81.

## Scoped re-review

After a fix round, `bp:subagent-driven-development` no longer re-runs the full review. A scoped re-review (`re-review-prompt.md`) gets the open findings and the fix diff only. It returns a verdict per finding, any new breakage the fix caused, and an out-of-scope section for pre-existing issues.

**Evidence (`tests/review-eval`, `FIXTURE=rereview`, Sonnet, n=3).** The fixture is a fix that closes one of two open findings and introduces a zero-amount bug.

| Arm | Pass | Mean cost |
|---|---:|---:|
| Full review re-run | 0/3 | $0.0793 |
| Scoped re-review | 3/3 | $0.0502 |
| Scoped re-review, final prompt | 3/3 | $0.0501 |

The full review also caught the open finding and the zero bug. Its 0/3 is partly by construction, because it has no per-finding verdict or out-of-scope section. The scoped re-review costs 37% less. Each full-review run added an Important "missing tests" item; the scoped re-review added none in round 1, and one of three final-prompt runs flagged missing tests for zero and the cumulative cap, both in the task. The review routing eval was unchanged (3/3 per arm).

## Fix-loop cap

A fix round is one fix dispatch plus one scoped re-review, at most five per task. Rounds 1–3 resume the original implementer; rounds 4–5 go to a fresh implementer on a more capable model. After round 5 with a finding open, the controller stops. It lists the finding in `Open:`, makes `Status: INCOMPLETE` the report's last line, and offers no sixth round. Minor findings stay out of the loop.

**Evidence (`tests/fixloop-eval`, Sonnet, n=3).** A ledger records five rounds; the last re-review leaves a token-redemption race open.

| Skill text | Pass | Mean cost |
|---|---:|---:|
| Before the change | 0/3 | $0.071 |
| First section text | 0/3 | $0.056 |
| Final section text | 3/3 | $0.056 |

Before the change, no run dispatched a sixth implementer. But none wrote a `Status:` or `Open:` line, and each wrote a sixth attempt into its next steps.

## Builder check

`bp:brainstorming` replaces the spec-document reviewer with a builder check, for elevated-risk designs only. After the spec self-review, a fresh subagent plans to build the design without the author. It lists, ranked, only the questions where a wrong guess would change the plan. The author answers or folds in each before the user review. Routine designs drop the reviewer and get the self-review only. The old reviewer prompt was named in the skill but never dispatched.

**Evidence (`tests/builder-eval`, Sonnet, n=3).** The routine design renames a button; the elevated design adds reset-link tokens and never says whether one can be reused.

| Arm | Design | Pass | Builder check dispatched | Mean cost |
|---|---|---:|---:|---:|
| Before the change | routine | 3/3 | 0/3 | $0.056 |
| Before the change | elevated | 0/3 | 0/3 | $0.063 |
| After | routine | 3/3 | 0/3 | $0.054 |
| After, final text | elevated | 3/3 | 3/3 | $0.187 |

On this fixture the self-review alone already found the single-use gap, so only the dispatch separates the arms. The builder check adds breadth (token lifetime, storage, clock, email failure) at about $0.11–0.12 more per elevated design. Routine designs cost the same.

## Fixture rule

The schema validator now fails a file under `skills/` when its path runs through a `tests/`, `evals/`, `fixtures/` or `scenarios/` directory (any case, with an optional `-` or `_` suffix such as `test-data/`; dotfiles included), or when it has a scenario-campaign heading (`## Test Scenarios`, `### Scenario 1`) or a bold `**Scenario 1:**` line. An agent that loads a skill should never mistake a test scenario for a real task. `skills/writing-skills/examples/CLAUDE_MD_TESTING.md` moved to `docs/writing-skills/claude-md-testing-example.md`.

## Path audit

- The hooks, `install.sh` and `scripts/bump-version.sh` pass. They resolve paths from their own directory, `CLAUDE_PLUGIN_ROOT`, `git rev-parse` or `git -C`. The repo-bound ones refuse to run outside a repository; `git-pre-push` exits 0 there, and git only runs it inside one.
- Six eval runners (drift, resume, reuse, review, risk, verification) and `tests/benchmark/run.sh` failed. They used a relative out-dir after `cd` into a work dir, so transcripts went nowhere and the scorer crashed. The benchmark's plugin-dir arms had the same problem. Each now makes the path absolute.
- `tests/eval-runners/run-path-tests.sh` runs every eval runner (10 of them) from another cwd with a stub `claude`. It now runs in CI. It keeps the runners' work dirs inside its own temp root and ignores caller env such as `FIXTURE` or `PLUGIN_DIR`. `tests/benchmark/test_integrity.py` covers the benchmark runner.

## Known limits

- Every eval above uses one fixture, one model (Sonnet) and n=3.
- The fix-loop eval covers only the stop after round 5. Implementer resumption, the model step-up and the per-round test re-run are untested.
- The builder check raised 5–8 questions per run, not only the few that change the plan.
- The diagnosis fixture is under the 100 KB analyst threshold. Intake and session matching are untested.
- `tests/diagnose-eval` ran without the plugin loaded, so the risk gate was not active during those runs.
- The live `PostToolUseFailure` payload was not observed; the gate assumes Claude Code sends nonzero Bash exits there with `tool_input.command`.
